# راهنمای توسعه

## مسئولیت‌ها

`web` مسئول نمایش و تجربهٔ کاربر است. `api` مالک قواعد قیمت، دسترسی، موجودی و پول است. `contracts` فقط قراردادهای عمومی را نگه می‌دارد؛ مدل Mongoose، اطلاعات محرمانه و منطق تأمین‌کننده نباید به فرانت صادر شوند.

در `api/src/modules` هر قابلیت هنگام پیاده‌سازی پوشهٔ خودش را می‌گیرد. فعلاً فقط health وجود دارد؛ برای قابلیت‌های ساخته‌نشده کلاس و پوشهٔ خالی تولید نمی‌کنیم.

## افزودن یک قابلیت

۱. قاعده و موارد مرزی را در سند تصمیم‌ها روشن کنید.
۲. ورودی و خروجی عمومی را با schema اعتبارسنجی در contracts تعریف کنید.
۳. مسیر HTTP ورودی را دریافت و اعتبارسنجی کند؛ قواعد کسب‌وکار در سرویس مربوط باشند.
۴. دسترسی Mongoose در فایل مدل/مخزن همان ماژول باشد؛ سیاست قیمت‌گذاری مستقیم به دیتابیس یا Express وابسته نباشد.
۵. کنترل عضویت و مالکیت داده در سرور انجام شود، نه فقط مخفی‌کردن دکمه.
۶. سناریوهای حساس و شکست را آزمایش کنید و `npm run check` و `npm run build` را اجرا کنید.

فقط در مرزهایی که نیاز واقعی دارند قرارداد یا interface می‌سازیم؛ مثلاً سرویس پیامک، نرخ ارز و درگاه. یک موتور قوانین عمومی یا مخزن generic برای همهٔ مدل‌ها نمی‌سازیم.

## TypeScript به زبان ساده

- `type` شکل داده را توضیح می‌دهد و در زمان اجرای JavaScript باقی نمی‌ماند.
- `strict` خطاهای احتمالی را پیش از اجرا آشکار می‌کند.
- `unknown` برای دادهٔ ناشناخته است؛ ابتدا باید آن را بررسی کرد.
- `zod` دادهٔ واقعی درخواست و پاسخ را هنگام اجرا بررسی می‌کند؛ TypeScript جای آن را نمی‌گیرد.
- در `contracts` از `z.infer` استفاده می‌کنیم تا نوع TypeScript از schema استخراج شود و دو تعریف جدا با هم ناسازگار نشوند.

## قواعد مالی و هم‌زمانی در مراحل بعد

- واحد داخلی پول باید صریح و ثابت باشد؛ تبدیل تومان به ریال فقط در مرز درگاه انجام شود.
- رزرو موجودی، مصرف کیف پول و ثبت رویداد مالی باید اتمیک و در برابر اجرای تکراری مقاوم باشند.
- عملیات چندسندی به MongoDB replica set و تراکنش نیاز دارد.
- کار ساعتی نرخ تتر و کار هفتگی تسویه باید در پردازش کارهای پس‌زمینه با کنترل اجرای تکراری پیاده شوند، نه یک timer در هر نمونهٔ وب‌سرور.
- قواعد مؤثر روی سفارش باید همراه سفارش نسخه‌برداری شوند؛ تغییر تنظیمات نباید قرارداد قبلی را تغییر دهد.

## مسیر توسعهٔ بعدی

۱. کاربران، ورود پیامکی و نشست‌ها؛ سپس عضویت فروشنده و دسترسی‌ها.
۲. دسته‌بندی، برند، محصول و تنوع با چرخهٔ تأیید.
۳. قیمت صنفی و سیاست تتر همراه با آزمون عددی.
۴. تعرفهٔ ارسال، سبد و رزرو موجودی.
۵. درگاه، سفارش و تحویل؛ سپس مرجوعی، کیف پول و تسویه.

در هر مرحله یک مسیر قابل‌آزمایش کامل می‌شود. پیش از افزودن endpoint دارای نشست مرورگر، سیاست cookie، CSRF، محدودیت درخواست و ثبت رخداد امن تکمیل شود. اسکلت فعلی احراز هویت یا آمادگی انتشار فروشگاه را ادعا نمی‌کند.

## Git و تحویل مرحله‌ای

پس از تکمیل یک مرحلهٔ قابل‌آزمایش، بررسی‌ها اجرا و تغییرات مرتبط commit می‌شوند. push فقط به remote مورد تأیید مالک پروژه انجام می‌شود؛ از force push استفاده نمی‌کنیم. فایل‌های محیطی، دادهٔ واقعی مشتری و اسرار نباید وارد commit شوند. جزئیات راه‌اندازی و تغییر قراردادها باید همراه کد به‌روز شوند.
