# ورود با موبایل: مرحلهٔ اول

## قابلیت‌های پیاده‌سازی‌شده

- یکسان‌سازی شمارهٔ ایران با ارقام فارسی، عربی یا لاتین به قالب +989….
- درخواست و تأیید کد شش‌رقمی؛ حساب فقط پس از تأیید کد ساخته می‌شود.
- نگه‌داری HMAC کد با کلید سرور؛ کد خام در دیتابیس، پاسخ API یا لاگ قرار نمی‌گیرد.
- محدودیت ارسال بر اساس موبایل و IP و محدودیت تلاش برای هر کد؛ شمارنده‌ها در MongoDB مشترک‌اند.
- مصرف اتمیک کد: تأیید هم‌زمان نباید چند نشست از یک کد ایجاد کند.
- نشست تصادفی در کوکی HttpOnly؛ در production با Secure، SameSite=Lax و پیشوند __Host-.
- نگه‌داری فقط هش نشست در دیتابیس، بررسی انقضا در هر درخواست و ابطال هنگام خروج.
- مسدودشدن حساب، دسترسی با نشست قبلی را هم قطع می‌کند.
- کنترل Origin برای درخواست‌های تغییردهنده و Cache-Control: no-store برای پاسخ‌های ورود.

## وضعیت پیامک

هنوز سرویس پیامکی انتخاب و متصل نشده است. `UnconfiguredSmsSender` عمداً پاسخ ۵۰۳ می‌دهد. برنامه هیچ کد ثابت یا در پشتی ندارد و موفقیت ارسال را شبیه‌سازی نمی‌کند. فرستندهٔ آزمایشی فقط در آزمون‌های یکپارچه و fixture مرورگر وجود دارد و کد را در حافظهٔ همان آزمون نگه می‌دارد.

اتصال واقعی باید رابط `SmsSender` را پیاده کند و timeout محدود، عدم ثبت کد و اسرار، بررسی پاسخ سرویس و رفتار مشخص در نتیجهٔ نامعلوم داشته باشد. retry خودکارِ کور می‌تواند پیامک تکراری ارسال کند. انتخاب سرویس و کلید آن مرحلهٔ بعد است؛ کلید فقط در محیط اجرا قرار می‌گیرد.

## مسیرهای API

- `POST /api/v1/auth/otp/request`: ورودی `{ mobile }`؛ خروجی ۲۰۲ شامل challengeId، زمان اعتبار و فاصلهٔ ارسال مجدد.
- `POST /api/v1/auth/otp/verify`: ورودی `{ mobile, challengeId, code }`؛ خروجی حساب عمومی و کوکی نشست، بدون توکن در بدنه.
- `GET /api/v1/auth/me`: حساب عمومی کاربر دارای نشست معتبر.
- `POST /api/v1/auth/logout`: ابطال نشست و پاک‌کردن کوکی، پاسخ ۲۰۴.

تمام POSTها نیازمند هدر Origin برابر WEB_ORIGIN هستند؛ درخواست بدون Origin نیز رد می‌شود. ورود برای همهٔ شماره‌ها یک پاسخ اولیهٔ عمومی دارد و وجود یا نبود حساب را افشا نمی‌کند. نقش فروشنده، مدیر یا دسترسی صنفی از ورودی ورود پذیرفته نمی‌شود.

## تنظیمات و استقرار

AUTH_SECRET باید تصادفی، محرمانه و حداقل ۳۲ کاراکتر باشد. برای تولید، در ترمینال شخصی خود اجرا کنید و نتیجه را فقط در `.env` قرار دهید:

```powershell
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

WEB_ORIGIN مبدأ دقیق فرانت و بدون اسلش پایانی است. فرانت و API در استقرار باید پشت مبدأ مشترک و HTTPS قرار بگیرند. فرم ورود فرانت و rewrite داخلی Next نوشته شده‌اند؛ فرانت با API و MongoDB واقعی در مرورگر بررسی شده است و تنظیم reverse proxy شبکهٔ استقرار باید جداگانه تکمیل شود.

سیاست‌های اولیه در `auth.policy.ts` متمرکزند: عمر کد ۱۸۰ ثانیه، ارسال مجدد پس از ۶۰ ثانیه، پنج تلاش برای هر کد، پنج درخواست در ساعت برای هر موبایل، ۳۰ ارسال در ساعت برای هر IP، ۱۰۰ تلاش تأیید در ساعت برای هر IP و عمر نشست هفت روز. این‌ها پیش‌فرض‌های اجرایی قابل‌تغییرند، نه تصمیم‌های دائمی محصول. درخواست ردشده یا ارسال ناموفق نیز ممکن است سهمیه مصرف کند تا retryهای پرتعداد کنترل شوند. پنجرهٔ سهمیه ساعتی ثابت است.

API فعلاً به X-Forwarded-For اعتماد نمی‌کند. پیش از استقرار چندلایه باید پراکسی‌های قابل‌اعتماد دقیقاً مشخص شوند؛ تنظیم `trust proxy=true` بدون شناخت مسیر شبکه مجاز نیست. در وضعیت فعلی کاربران پشت یک پراکسی در سهمیهٔ همان IP شریک خواهند بود. آزمون بار و سیاست شبکه پیش از انتشار لازم‌اند.

برای تضمین یکتایی موبایل، ایندکس‌ها پیش از آغاز سرویس ساخته می‌شوند. MongoDB باید مجوز ساخت ایندکس داشته باشد. مهاجرت آیندهٔ ایندکس روی دادهٔ حجیم باید جدا از startup برنامه‌ریزی شود.

TTL فقط پاک‌سازی است؛ انقضا همیشه در query بررسی می‌شود. اگر بعد از مصرف کد، ایجاد حساب یا نشست به خطا برسد، کد دوباره قابل‌استفاده نمی‌شود و مشتری باید کد تازه درخواست کند.

## آزمون‌ها

```powershell
npm run check
npm run test:integration
npm run build
```

آزمون یکپارچه MongoDB را از TEST_MONGODB_URI یا localhost می‌خواند، ولی همیشه یک دیتابیس تصادفی با پیشوند `raqs_auth_test_` می‌سازد و فقط همان دیتابیس را در پایان حذف می‌کند. آن را با دسترسی محدود توسعه/CI اجرا کنید. آزمون‌ها پیامک واقعی نمی‌فرستند.

## کارهای باقی‌مانده

اتصال پیامک واقعی، تأیید آزمون‌های فرم ورود، انتخاب و اعمال تنظیمات شبکهٔ استقرار، تکمیل احراز هویت دومرحله‌ای پنل فروشنده، مدیریت عضویت و مجوزها. ورود مشتری به‌تنهایی مجوز مدیریت یا خرید صنفی نمی‌دهد. این مرحله به معنی آماده‌بودن سامانهٔ فروش برای انتشار نیست.

مراجع طراحی: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)، [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) و [Mongoose atomic updates](https://mongoosejs.com/docs/8.x/docs/tutorials/findoneandupdate.html).
